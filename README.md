# kryzhov-profile-gql

Цифровая визитка: GraphQL API на NestJS, Prisma и PostgreSQL. Отдаёт мой профиль, навыки, опыт работы и проекты.

## Запуск в Docker

Нужны Git и Docker с Docker Compose.

```bash
git clone https://github.com/liringlas/kryzhov-profile-gql.git
cd kryzhov-profile-gql
cp .env.example .env
docker compose up --build
```

При старте контейнер применяет миграции и заполняет базу из `src/seed/profile.json`. Apollo Sandbox: http://localhost:3100/graphql (порт задаёт `APP_PORT` в `.env`).

## Запуск приложения без Docker

Нужен Node.js 24. Nest CLI и Prisma CLI ставить глобально не надо, они устанавливаются вместе с зависимостями проекта.

```bash
cp .env.example .env
docker compose up -d db     # только PostgreSQL
npm ci                      # postinstall генерирует Prisma Client
npx prisma migrate deploy
npx prisma db seed
npm run start:dev
```

## Данные на русском и английском

По умолчанию база заполняется на русском из `src/seed/profile.json`. Английская версия лежит в `src/seed/profile.en.json`:

```bash
cp src/seed/profile.en.json src/seed/profile.json
docker compose up --build   # без Docker: npx prisma db seed и перезапуск приложения
```

Вернуть русский: `git checkout src/seed/profile.json`.

Имя профиля служит первичным ключом и значением аргумента `name` по умолчанию, поэтому зависит от языка: «Константин Рыжов» в русской версии, «Konstantin Ryzhov» в английской. Запрос без `name` вернёт профиль, который сейчас в базе, а с именем из другой версии вернёт `null`.

## Пример запроса

```graphql
query {
  profile {
    name
    description
    links {
      name
      url
    }
    skills {
      name
    }
    experiences {
      company
      title
      startDate
      endDate
      achievements {
        description
      }
    }
    projects {
      name
      description
      url
    }
  }
}
```

## Архитектурные решения

- **Один модуль Profile**. Ссылки, навыки, опыт с достижениями и проекты не существуют без профиля, поэтому отдельные модули, репозитории и резолверы для каждой сущности в приложении решено не делать, так как приложение очень маленькое. Выносить сущность отдельно стоит, когда у неё появится собственный API.
- **Три слоя внутри модуля**. Резолвер описывает GraphQL API -> Сервис отвечает за логику -> Репозиторий — единственное место, которое обращается к базе через Prisma. GraphQL-модели лежат в одной папке, по файлу на тип.
- **Схема из кода.** Схема GraphQL строится из TS-классов и коммитится в `schema.gql`, чтобы изменения API были видны в истории. Поля повторяют модель базы, поэтому опыт работы называется experiences, а должность — title. Это немного отличается от примера схемы из задания.
- **Связи загружаются по запросу**. Каждая связь профиля — отдельный резолвер поля который вызывается только если клиент запросил это поле: запрос одного имени — один SQL-запрос, полный профиль — шесть. `achievements` приходят вместе с `experiences` одним запросом на все места работы.
- **Без DataLoader**. У схемы один корень и нет циклов, поэтому проблема N+1 здесь не возникает. DataLoader и ограничение глубины запроса понадобятся, когда появится список профилей или обратная связь от навыка к профилям. Я подумывал для демонстрации DataLoader'а подключить вложенную схему типа `profile { skills { profile { skills } } }`, так как у `skill` связь с `profile` m-n, но отказался от этой идеи.
- **Миграции и сид при старте**. Схема базы меняется только миграциями из репозитория. Контейнер применяет их, заполняет базу и только потом запускает приложение.
- **Данные профиля в JSON**. Структура файла валидируется схемой zod. Сид пересоздаёт данные в одной транзакции, поэтому безопасно запускается на каждом старте, а правки в JSON попадают в базу при следующем деплое.
